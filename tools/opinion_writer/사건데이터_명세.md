# 사건 데이터 명세

`dialogue_flow.py start`가 대화에 연결된 빈 구조를 생성합니다. ID는 사건 내에서 고유하게 유지합니다. JSON은 UTF-8이며 원문 파일은 사건의 `원문/`에 보존합니다. 법적 판단이나 원문 해석은 필드 검증만으로 확인되지 않습니다.

| 최상위 키 | 내용 |
|---|---|
| schema_version | 2 |
| case_id / mode | 영문·숫자 사건 ID / real 또는 demo |
| notice | 공문명·번호·시행일·수령일·기한·처분청·부서·제출방법, 위반별 sanctions 배열. stage는 pre_notice 또는 hearing_notice |
| procedure | kind: general / hearing / fine / special / unconfirmed. analysis: 적용 판단. law_ids: 확인한 L ID. form: 서식 선택 |
| sources | id, role(notice/consultation/evidence/form), path(사건 폴더 상대경로), sha256, received_at |
| facts | id, text, status, source_refs 배열 |
| legal_review | id, citation, source_url, source_excerpt, as_of, version, checked_at, analysis, status |
| issues | id, title, finding, law_ids, questions 배열. 감경·면제·갈음 불가/미확인 판단도 기록 |
| arguments | id, title, body, status, fact_ids, law_ids, evidence_ids, review |
| evidence | id, title, purpose, request, scope, holder, due_date, alternative, status, source_ids, finding, review_note, include_in_attachment |
| draft.fields | 표지의 당사자·주소·전화·작성일·문서번호·수신 및 별지의 취지·결어 등 |
| workflow | version, audience, criteria, questions, answers, checklists, responses. 질문지와 답변의 대화 흐름 |
| document_review / events | 현재 내용의 검토 기록 / 변경 사건. 프로그램이 기록 |

## 사실 기록

```json
{"id":"F001","text":"상담자가 말한 구체적 사실","status":"reported",
 "source_refs":[{"source_id":"S002","locator":"상담기록 14~18행, 14:23 진술"}]}
```

상태는 `reported` 진술만 확인 / `verified` 증빙과 대조 / `disputed` 상충 또는 다툼 / `unknown` 미확인입니다. 공문의 주장도 사실 확정과 구별하여 `reported`로 기록하고 주체를 밝힙니다. `disputed`·`unknown`을 인용한 본문에는 `【확인 필요】`를 넣어야 합니다.

## 논거와 자료 연결

```json
{"id":"A001","title":"이 사건의 구체적인 소명 제목","body":"검토한 소명 문단\n\n두 번째 문단",
 "status":"active","fact_ids":["F001"],"law_ids":["L001"],"evidence_ids":["E001"],"review":{}}
```

`active`만 별지에 출력합니다. `hold` 보류·`withdrawn` 철회는 내부 대조표에 남깁니다. E ID는 Evidence를 뜻하는 작성기의 내부 관리번호이며 법정 서식의 번호가 아닙니다. 내부 ID는 변경하지 않고, PDF·DOCX와 의뢰인용 요청목록에는 `소명자료 1`, `소명자료 2`처럼 표시합니다. 필요 없는 자료를 철회하면 관련 논거에서 참조를 제거하거나 철회 사실을 반영합니다.

표시번호는 해당 버전에서 사용하는 자료에 부여하며 검토 완료·첨부 예정 자료를 먼저 배열합니다. 본문의 참조와 목록에 같은 번호를 사용하고 `소명자료_번호대조표.json`에 E ID와 표시번호의 관계를 보존합니다. 명시적인 `[E001]` 참조 토큰도 표시번호로 변환합니다. 제품 모델명처럼 일반 문장에 쓰인 `E001`은 임의 변경하지 않습니다.

자료 상태는 `planned` 요청 예정 / `requested` 요청함 / `received` 수령·미검토 / `verified` 검토 완료 / `unavailable` 확보 불가 / `replaced` 교체 / `withdrawn` 철회입니다. 검토 결과 `finding`은 `supports` 지지 / `partial` 부분 일치 / `contradicts` 불일치 / `unreviewed` 미검토입니다. `verified`는 주장이 참이라는 의미가 아니라 **자료를 읽고 평가했다는 의미**이며 불일치도 검토 결과로 기록합니다.

`include_in_attachment=true`는 검토 완료한 자료의 첨부 예정 지정입니다. 실제 PDF 합본·외부 발송·접수 완료를 뜻하지 않습니다. 실물을 받지 않은 자료를 수령·검토 완료로 표시하면 생성이 차단됩니다.

## 서식 선택

일반 의견제출의 법적 적용을 확인한 경우:

```json
{"kind":"general","analysis":"사건 절차와 적용 여부를 검토한 이유","law_ids":["L001"],
 "form":{"type":"standard11","reviewed":true,"basis":"확인한 서식 적용 근거"}}
```

기관별 서식의 경우 원본 PDF를 `add-source --role form`으로 넣고 다음 구조를 사용합니다.

```json
{"type":"custom","reviewed":true,"basis":"기관 서식 및 근거 확인 내용",
 "source_id":"S003","boxes":{"의견제출인_성명":[0,120,150,350,24,10,"left"]}}
```

좌표는 `[0부터 시작하는 쪽번호, 왼쪽, 위, 너비, 높이, 글자크기, 정렬]`이며 pt 단위입니다. 실제 원본과 채움 후 PDF를 확인해야 합니다. 잘못된 쪽번호·범위 밖 좌표는 오류입니다. 원문 경로·좌표를 지어내지 않습니다. 적용 미확정 시 `type=unconfirmed`를 사용하면 일반 초안 표지만 생성합니다.

## 검토와 변경

법령은 `status=verified`일 때 원문 요지·공식 URL·기준일·시행 버전·조회시각·적용 이유가 필요합니다. 도구 조회 없는 상태에서 verified로 표시하지 않습니다. 프로그램은 입력된 검토 기록의 충족 여부를 확인하며 실제 법령 도구 호출을 대신하지 않습니다.

`review`는 원문·사실·법령·증빙·본문·서식의 현재 값에 대한 지문을 저장합니다. 이후 값이 바뀌면 관련 주장과 문서 전체 검토가 다시 필요합니다. 날짜·수치·소명 범위를 변경한 경우에는 취지와 결어까지 확인합니다. `review`를 재실행하기 전에 담당 AI 또는 행정사가 **본문을 수정하거나 유지하는 이유를 기록**합니다.

## 질문지와 답변의 연결

`workflow.audience`: `professional`(행정사용) 또는 `self`(본인용).

```json
{
  "criteria": [{"id":"C1","category":"mitigation","title":"감경 요건",
    "requirement":"확인한 해당 법규의 요건", "analysis":"이 사건에서 확인할 이유",
    "assessment":"possible","law_ids":["L001"]}],
  "questions": [{"id":"Q1","question":"요건을 확인할 구체적인 질문",
    "why":"확인 이유","criterion_ids":["C1"],"evidence_request":"확인할 자료"}],
  "answers": [{"question_id":"Q1","state":"answered","answer":"원문 범위의 답변",
    "source_refs":[{"source_id":"S002","locator":"답변 2행"}]}]
}
```

`category`는 `non_imposition`(불처분·예정 처분 변경), `mitigation`(감경), `exemption`(면제), `substitution`(과징금 등 대체), `procedure`(절차)입니다. 불처분·변경과 감경은 항상 검토하며 제도가 없거나 확인되지 않았으면 그렇게 기록합니다.

`assessment`는 `possible`(요건 확인 대상), `not_applicable`(현재 확인 범위에서 적용 곤란), `unknown`(추가 검토 필요)입니다. 가능/곤란 판단에는 확인한 법규와 원문·출처·시행 버전이 필요합니다. ‘가능’은 결과 보장이 아닙니다. 각 요건에는 적어도 한 질문이 연결되어야 합니다.

`answers.state`는 `answered`, `not_applicable`, `unknown`입니다. 답변과 해당 없음 판단에는 받은 답변 원문의 출처가 필요합니다. 답변하지 않은 Q도 생략하지 말고 확인 필요로 기록합니다.

프로그램이 `checklists`에 QSET 번호·공문/법규/질문의 해시·경로를, `responses`에 해당 질문지와 원문 ID 연결을 기록합니다. 이 기록은 임의로 만들지 않습니다. 질문·공문·관련 법규가 바뀌면 새 QSET를 생성하고 답변을 재대조합니다. 새 증빙만 추가한 때는 질문이 바뀌지 않았다면 관련 논거와 문서의 재검토로 진행할 수 있습니다.

같은 대화의 사건은 `산출/대화연결/`에 분리하여 연결합니다. 새 사건은 새 대화키를 사용하거나 사용자가 새 사건임을 확인한 뒤 `--new-case`로 연결합니다. 서로 다른 대화의 최신 사건을 자동 선택하지 않습니다.
