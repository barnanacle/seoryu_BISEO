# 반복 서식 작성

법정 서식 PDF는 원본 그대로 두고, 꾸러미의 좌표와 작성요령에 따라 값을 얹습니다. 먼저 꾸러미가 있는지 확인합니다. 없으면 사건별 임시 빌더를 새로 짜지 말고 [꾸러미 만들기](references/create-pack.md)를 따릅니다. 실제 사건 자료와 산출물은 공개 저장소에 넣지 않습니다.

## 시작 전에

1. 현재 프로젝트의 `AGENTS.md`와 사건 폴더 지침을 먼저 읽습니다.
2. `python3 tools/form_engine/bin/build.py --list-packs`로 꾸러미를 확인하고, 해당 `tools/form_packs/<id>/guide.md`에서 적용 범위·출처·필드를 확인합니다. 처분 사전통지 상담 흐름은 기존 `tools/opinion_writer/사용_시퀀스.md`를 따릅니다.
3. 맞는 꾸러미가 없으면 공식 원본과 작성요령을 확인한 후 새 꾸러미를 제안합니다. 서식의 현행성과 적용 여부를 임의로 단정하지 않습니다.

## 작성 절차

1. 기관 원문·상담기록·꾸러미 작성요령을 대조합니다. 사용자가 정한 신청·대응 방향은 임의로 바꾸지 않습니다.
2. 법령 조회에는 법령명·조문·별지 번호만 넣습니다. 업체명, 개인명, 주소, 연락처, 사건번호는 외부 도구나 웹 검색에 넣지 않습니다.
3. `python3 tools/form_engine/bin/build.py --pack <id> --keys`로 현재 필드를 확인하고 사건 폴더에 `fields.json`을 작성합니다. 공개 예시와 실제 사건 입력은 분리합니다. 확인하지 못한 값은 추측하지 않고 `【확인 필요】`로 남깁니다.
4. `python3 tools/form_engine/bin/build.py fields.json --pack <id> --no-open`으로 생성·검증합니다. 기존 의견제출서 명령 `python3 tools/opinion_writer/bin/build_pdf.py fields.json --no-open`도 계속 사용할 수 있습니다.
5. 제출용 PDF와 전체 편집 DOCX를 확인합니다. 별지가 `narrative`면 합본될 수 있고, `list`는 내부 점검표로 별도 생성될 수 있으며, `none`이면 없습니다. 각 꾸러미의 `append_to_submission` 설정과 `guide.md`를 우선합니다.
6. HWP·HWPX는 별도 요청과 지원 경로가 있을 때만 만듭니다.

## 필수 검증

- 모든 공식 서식 쪽의 선·문구·유의사항·서명란과 PDF 쪽 수를 확인합니다. 벡터 합치기인지 래스터 대체인지 보고합니다.
- 남은 `{{필드명}}`, `【확인 필요】`, 잘림·겹침·빈 페이지를 PDF와 DOCX 렌더링으로 확인합니다.
- 실제 확보한 자료만 붙임 목록에 넣습니다. 내부 점검표를 공식 붙임이라고 설명하지 않습니다.
- 결과 경로, 미확인 항목, 근거, 래스터 대체 여부를 보고하고 행정사 검토 전에는 제출 완성본이라고 표현하지 않습니다.

## 공개·공유 금지

실제 `fields.json`, 기관 원문, 상담기록, 사건별 참고본, 렌더 이미지, 중간 파일, 완성 PDF·DOCX를 공개 저장소나 스킬 폴더에 넣지 않는다. 공유 가능한 것은 익명화한 지침, 필드명, 빈 템플릿, 범용 검사 도구뿐이다.
