# 반복 서식 작성

법정 서식과 별지의 내용을 한 번만 정리해 서로 일치하는 제출용 PDF와 편집용 DOCX를 만든다. 실제 사건정보가 포함된 원본·입력값·산출물은 현재 사건 폴더 안에서만 다룬다.

## 시작 전에

1. 현재 프로젝트의 `AGENTS.md`와 사건 폴더의 추가 지침을 먼저 읽는다.
2. 기관 원문, 상담기록, 빈 법정 서식, 별지 템플릿, 형식 참고본의 위치를 확인한다.
3. 프로젝트에 `bin/build_pdf.py`가 있으면 그 도구와 로컬 지침을 우선한다. 없거나 새 서식에 맞게 구현해야 하면 [구현 지침](references/implementation-guide.md)을 읽는다.
4. 원본·서식·참고본·기존 도구는 직접 수정하지 않는다. 결과는 프로젝트가 지정한 산출 폴더에 새 파일로 만든다.

## 작성 절차

1. 기관 원문과 상담기록을 처음부터 끝까지 읽고 처분 내용, 당사자, 원인, 근거 조문, 제출기한, 제출처, 문서번호를 출처와 함께 정리한다.
2. 사용자가 정한 신청·대응 방향은 임의로 바꾸지 않는다. 확인된 사실과 법적 근거만 보강한다.
3. 법령 도구에는 법령명·조문·별표 번호만 보낸다. 업체명, 대표자명, 주소, 연락처, 사건번호, 문서번호는 외부 도구나 웹 검색에 넣지 않는다.
4. 프로젝트에 빌더가 있으면 먼저 `python3 bin/build_pdf.py --keys`로 현재 필드 목록을 확인한다. 코드에 기억한 필드 목록을 강제로 적용하지 않는다.
5. 모든 값을 문자열로 넣은 `산출/fields.json`을 만든다. 서로 충돌하는 값은 출처를 대조하고, 확인되지 않은 값은 빈 문자열로 두거나 `【확인 필요】`로 표시한다. 추측하지 않는다.
6. 본문형 값은 빈 줄로 문단을 구분한다. 단정적 표현을 피하고 상담기록과 공식 자료에서 확인된 사실만 쓴다.
7. 프로젝트 빌더가 있으면 `python3 bin/build_pdf.py 산출/fields.json --no-open`으로 먼저 생성·검사한다. 검사가 끝나고 사용자가 화면 확인을 원하면 `--no-open` 없이 다시 실행할 수 있다.
8. 다음 산출물을 확인한다.
   - 법정 서식 원본 위에 값이 얹힌 첫 페이지
   - 서술형 별지가 뒤에 이어진 제출용 PDF 한 파일
   - 같은 값으로 만든 편집용 별지 DOCX
9. HWP 또는 HWPX는 사용자가 명시적으로 요구하고 프로젝트가 별도 경로를 제공할 때만 만든다.

## 필수 검증

- 첫 페이지의 공식 서식 선·문구·유의사항·서명란이 바뀌지 않았는지 확인한다.
- 벡터 원본과 오버레이를 합치는 방식이 성공했는지 확인한다. 래스터 배경으로 대체되었다면 숨기지 않고 보고한다.
- 법정 서식과 별지의 명칭, 주소, 건명, 날짜, 처분청이 같은 `fields.json` 값과 일치하는지 확인한다.
- 남은 `{{필드명}}`, `【확인 필요】`, 잘린 글자, 겹친 글자, 빈 페이지, 비정상 페이지 크기를 검사한다.
- 별지의 페이지 수를 미리 고정하지 않는다. 내용 길이에 따라 늘어나는 것을 허용하되 제목과 서명이 어색하게 분리되지 않았는지 렌더링으로 확인한다.
- 실제 확보한 자료만 소명자료 목록에 넣는다.
- 생성된 PDF와 DOCX의 경로, 미확인 항목, 사용한 출처, 래스터 대체 여부를 짧게 보고한다.
- 행정사가 검토하기 전에는 의뢰인에게 보낼 완성본이라고 표현하지 않는다.

## 공개·공유 금지

실제 `fields.json`, 기관 원문, 상담기록, 사건별 참고본, 렌더 이미지, 중간 파일, 완성 PDF·DOCX를 공개 저장소나 스킬 폴더에 넣지 않는다. 공유 가능한 것은 익명화한 지침, 필드명, 빈 템플릿, 범용 검사 도구뿐이다.
